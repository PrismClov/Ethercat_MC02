# EtherCAT 2 kHz 抓包实时性测试

## 测试环境

| 项目 | 配置 |
|---|---|
| 主站 | SOEM 2.0.0，Linux 5.15.148-tegra，aarch64 |
| 主站调度 | CPU5，SCHED_FIFO 80，锁定内存 |
| 网卡 | enP8p1s0，100BASE-TX 全双工 |
| 网卡中断 | CPU0，未与主站线程共核 |
| 从站 | 达妙 MC02 / LAN9252 |
| 从站状态 | OP，WKC=3 |
| 控制周期 | 500 us（2 kHz） |
| 抓包工具 | Wireshark dumpcap/tshark 3.6.2 |
| 抓包时长 | 30.151 s |
| 抓包文件 | `build/soem_master/ethercat_2k.pcapng` |

抓包只保留 EtherType `0x88a4`，接口统计为接收 121217、丢弃 0。

## 报文结构

每个周期的主站发送帧和从站返回帧均为 661 Byte，结构为：

```text
Ethernet II:
  Destination MAC : ff:ff:ff:ff:ff:ff
  EtherType       : 0x88A4
EtherCAT frame:
  Length          : 0x285
  Type            : EtherCAT command
  LRW             : 613 Byte logical read/write process data
  FRMW            : 8 Byte, 0x0910 DC System Time
```

主站帧的 LRW WKC 为 0，从站返回帧的 WKC 为 3，符合单从站收发和
DC System Time 读取方式。

> 当前 SOEM 构建使用默认主站 MAC `01:01:01:01:01:01`。该地址在 IEEE
> 802.3 中属于组播地址，Wireshark 会给出源 MAC 警告；这不影响 EtherCAT
> 通信，但正式测试可在构建 SOEM 时通过 `EC_PRIMARY_MAC` 使用网卡真实
> 单播 MAC。

| 指标 | 结果 |

| 双向字节率 | 2.645 MB/s |

Wireshark 同时看到发送帧和从站返回帧，因此双向报文率约为控制周期率的

## 周期与抖动

使用 Wireshark 导出主站 LRW 帧的软件接收时间戳，并对相邻帧求差：

| 指标 | 周期差值 |
|---|---:|
| 最小值 | 234.842 us |
| 平均值 | 500.000 us |
| 中位数 | 499.725 us |
| P95 | 511.169 us |
| P99 | 521.660 us |
| 最大值 | 761.509 us |
| 标准差 | 7.157 us |

60302 个发送间隔中，超过 550 us 的有 43 个（0.071%），超过 600 us 的
有 17 个，超过 700 us 的只有 1 个。最大样本为 761.509 us，紧随其后的
间隔为约 235 us，两个间隔之和仍接近两个名义周期。这更像软件抓包时间戳
的单次错位，而不是整帧丢失；但它仍说明发帧时间没有严格锁定在
500 us 网格上。

同时从 FRMW/0x0910 读取 64 位 DC System Time，对相邻主站帧的 DC 时间
增量减去名义周期 500 us：

| 指标 | DC 抖动 |
|---|---:|
| 平均值 | +0.018 us |
| 中位数 | -0.360 us |
| P5 | -10.400 us |
| P95 | +13.920 us |
| P99 | +27.560 us |
| 99% 区间 | 约 -17.6～+27.6 us |
| 标准差 | 8.398 us |
| 最大绝对值 | 269.920 us |

约 99.17% 的样本处于 ±30 us 内，但仍有约 0.83% 的尖峰超出该范围。
最大样本附近伴随一次短暂的 SM watchdog；主站采用非阻塞恢复后继续维持
约 2 kHz 的 PDO 发送。其他尖峰同时包含软件采样、抓包调度和 DC 时间
读取抖动，不能全部归因于 DC 时钟本身。

## 帧周转时间

将主站 LRW 帧与紧随其后的从站返回帧配对，得到接口处的帧周转时间：

| 指标 | 时间 |
|---|---:|
| 平均值 | 117.149 us |
| 中位数 | 116.110 us |
| P95 | 131.845 us |
| P99 | 151.634 us |
| 最大值 | 395.060 us |

该时间包含以太网发送、从站处理、返回方向和软件时间戳误差，不等同于
PHY 单向传播延迟。661 Byte 帧在 100 Mbit/s 下每个方向的串行化时间约
52.9 us，因此约 117 us 的双向周转符合当前帧长和链路速率。

## FIFO 80 与 FIFO 99 对比

FIFO 99 测试临时将 `sched_rt_runtime_us` 设为 `-1`，主站固定 CPU5，
测试后已恢复为系统默认 `950000`。两次测试使用相同的 2 kHz 周期和
661 Byte 过程数据帧。

| 指标 | FIFO 80 | FIFO 99 |
|---|---:|---:|
| 抓包时长 | 30.151 s | 60.390 s |
| 发送间隔 P99 | 521.660 us | 520.229 us |
| 发送间隔最大值 | 761.509 us | 1162.052 us |
| DC 抖动 P5 | -10.400 us | -9.440 us |
| DC 抖动 P95 | +13.920 us | +12.240 us |
| DC 抖动 P99 | +27.560 us | +25.280 us |
| DC 抖动标准差 | 8.398 us | 8.382 us |
| DC 抖动最大绝对值 | 264.760 us | 662.880 us |
| 抖动超过 100 us 的比例 | 0.0547% | 0.0621% |
| 抖动超过 200 us 的比例 | 0.0066% | 0.0166% |
| WKC=1 突发 | 1 次 | 1 次 |

提升到 FIFO 99 后，主体 P95/P99 有约 1～2 us 的改善，但长尾明显恶化。
结果说明问题不只是普通任务抢占主站线程，而是仍存在硬件中断、内核软中断、
驱动处理、内存/RCU 等非应用优先级可消除的延迟。禁用 RT throttling 也没有
消除 watchdog，因此不建议把 FIFO 99 当成实时性的根本解决方案。

## 限制

- `enP8p1s0` 只有软件时间戳，没有 PTP 硬件时钟，因此抓包时间戳包含
  Linux 调度和内核收包误差。
- 普通 PDO 帧没有独立业务时间戳，DC 抖动由 FRMW 读取的 `0x0910`
  系统时间增量计算。
- 本次没有隔离网卡中断以外的全部内核任务，也没有使用 PREEMPT_RT
  内核；硬实时认证需要在目标生产系统上重新测试。

## 结论

2 kHz 下约 99% 的 DC 时间增量处于 ±30 us 内，带宽和协议层通信正常，
但测试期间仍出现一次 WKC 丢失和随之而来的 SM watchdog/Safe-Op 切换。
对于伺服闭环，250～270 us 的时序尖峰已经不可忽略，可能使过程数据错过
当前 SYNC0 输出锁存窗口。

因此本次结果可以证明 EtherCAT 通信和 SOEM 主站链路可用，但**不能据此
认定普通 Linux + 用户态 SOEM 已满足 2 kHz 硬实时运动控制要求**。生产
控制建议使用 PREEMPT_RT 或 IgH 主站，加入严格 deadline-miss 检测，
并把发送任务与 SYNC0 相位锁定；在完成这些改造前，建议使用 1 ms 周期
或只进行监视和低实时性控制。

FIFO 99 的对照抓包表明，仅提高用户线程优先级不能通过 2 kHz 硬实时验收。
下一步应使用匹配 Jetson T234/JetPack 的 PREEMPT_RT 内核，并隔离 CPU5、
迁移管理 IRQ 后重新执行同一套 60 秒测试。
